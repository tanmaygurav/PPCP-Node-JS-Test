## Trusted test data

An active administrator creates a run at `/admin/test-runs` and assigns registered synthetic fixture UIDs (`m04-poc-<8 hex>-sN`, `fN`, `aN`, `faculty` or `admin`). Normal registration cannot create server test markers. The existing synthetic account provisioning tool creates independent verified fixtures without sending registration mail. No real accounts or data are migrated or retrospectively marked.

The server derives immutable run IDs for upload operations, submissions, remarks and Drive app properties. Titles and filenames display `[LOAD TEST · <short ID>]`; title text alone never authorizes deletion. Titles retain their prefix during edits. Admin list filters select marked data or a run. List/detail badges and individual deletion links distinguish test records. Synthetic members cannot edit unmarked/foreign-run data; closing a run blocks new preparation and transaction commits. Existing unmarked fixtures and PP039 remain excluded.

Admin APIs under `/api/admin/test-runs` create/list/inspect/close runs. `/api/admin/test-cleanup` starts operation-ID-bound cleanup jobs; job GET and POST `/:id/retry` expose/resume progress. Every request checks current admin access. Run lists and inventories use cursor pages; cleanup uses bounded batches and a lease. Confirmation requires `DELETE TEST DATA`.

Cleanup closes selected runs, inventories **all** their upload operations (including abandoned/replaced/failed saves), deletes only trusted submissions/remarks, and moves matching files to **Drive Trash**. Current references and M04 folder/owner/run/app properties are checked before trashing. The app save window is one hour, but Drive resumable sessions can last one week. Session deadlines are recorded before external initiation with an extra one-hour safety margin. Completed metadata-verified files can be trashed immediately; absent unfinished files remain pending until the provider-session deadline, then inventory is checked again. Missing/already-trashed files are safe. Errors show remaining file IDs and require retry. Completion requires no pending file tasks or selected submissions. PP numbers are never reset/reused. Reusable accounts, sanitized reports and minimal operational metadata remain; no prior-content snapshots or backups are created.

## Conditions and safety

Each run records scenario, users, source/origin, duration, dataset target, think time and attachment mix; the report adds actual dataset size, timestamps, role counts, request rate/concurrency, generator CPU/event-loop pressure and outcomes. A first-observed instance marker is a startup observation, not proof of all cold starts. Browser observers reuse a workload identity; metadata-only writer scenarios also use a separately identified faculty review controller.

Ladder: **1 → 5 → 10 → 20 → 40 → 60 → 90 → 120**, optionally **160 → 200**. Scenarios are baseline, browsing, metadata, mixed, arrival and separate ten-file batches at 1/5/20. Normal windows last 180 seconds with 10–20-second think times. Each mixed student creates once and edits once, then browses. Mixed roles approximate 90/8/2; levels below three cannot represent three simultaneous roles. File mix: 70% none, 25% one 1 MB, 5% two 5 MB; exact integer distribution is reported. Ten-file tests use ten 1 MB files. Setup/sign-in is outside normal windows; arrival tests time simultaneous sign-in/session creation separately. Browser observers measure usable list/detail time alongside API load.

List/detail p95 targets are individually 2 seconds; create/edit saves individually 3 seconds, including validation/sharing but excluding transfer. Full response consumption, retries/errors/timeouts and full save workflows are recorded. SDK spans overlap: do not sum them. Transfer and browser timings are separate. Successful-request percentiles are accompanied by failure counts. Small samples are not strong p95 evidence.

Stop immediately on integrity failures, unresolved writes, quota/auth/server errors (including recovered Drive errors), non-draining work, event-loop p95 above 200 ms or metadata p95 above 10 seconds. A latency-only failed level permits one next diagnostic level, then stops escalation if that level also misses. Such levels are never accepted capacity. Retries are limited to two, reuse operation IDs and retain original timings. Test runs close even after a stopped workload.

Daily ceilings: 10,000 document reads, 3,000 writes/deletes and 1 GB uploads, further limited to 25% of verified remaining provider allowances. A rolling ignored ledger reserves concurrent requests and at least 600 operations, increased with fixture/run creation, for cleanup. The initial batch doubled SDK counts provisionally. After owner-dashboard reconciliation, future charging uses observed SDK operations plus a query-index surcharge; all historical charges and the explicit provider reconciliation remain in the ledger. These are **not provider billing**; index-entry billing and internal activity can differ. Drive per-user/project rate reservations, Vercel invocation/CPU/memory/transfer estimates, and browser API calls are included. Memory accounting conservatively uses 4 GB times request duration; it is not billed-memory attribution. Never delete the ledger to bypass a stop. Split across days and refresh usage as needed. Spark stays enabled and billing upgrades remain disabled.

Interrupted jobs resume from ignored checkpoints. Alternatively use the administrator screen's per-run/all-run/individual controls. Retry waiting jobs after expiry; verify completion before claiming cleanup finished.

After Preview acceptance, obtain one owner-confirmed quiet Production window. Deploy the verified source with canonical origin and validate up to the highest accepted level, subject to the same budgets. Never pass `--production-window` without that agreement. ## Event guidance and interpretation

- Users: prepare files before entry; prefer smaller files within the enforced limits; save once; keep the page open during upload; use **Retry same save** after an interrupted acknowledgment instead of creating another submission. Do not repeatedly refresh or double-submit.
- Organizers: use the highest **repeatably passing and Production-validated** level, with headroom; stagger arrivals and large uploads, schedule faculty bulk review away from submission bursts, and pause new entry on widespread errors or quota pressure. Until measured, 120 is a target, not an operating promise.
- Admins: inspect conditions/results, close runs, preview cleanup counts, confirm deletion, and resume until no eligible leftovers remain. Earlier unmarked fixtures are intentionally outside bulk cleanup.
- Forecast assumption: 500 creates with the chosen mix produce roughly **375 MB / 175 files**, before replacements. Model one edit, one remark and lock/unlock per submission plus measured browsing. Derive Firestore operation forecasts from complete measured workflows, separating test-only guards/control traffic from normal event assumptions.
- Change one factor at a time. Startup: imports/SDK/platform; authentication: arrival bursts/duplicate calls; queries: indexes/payload/pages; transactions: sequence-counter contention; Drive metadata/sharing: call count and owner quota; transfer: verify another connection; browser: bundle/render/request duplication. A client/server timing gap alone does not identify Vercel as the cause. Provider replacement or paid upgrades require evidence and a separate decision.

### Where requests originate

The generator is local Node.js on the owner's Windows machine, using its internet connection to call the hosted Vercel Preview or canonical Production origin. Most simulated users are independent authenticated API sessions; a headless Chromium observer performs real portal journeys alongside them. This is not one browser/device per active user, and traffic is not generated inside Vercel. Hosted application code runs in Vercel's Mumbai functions and calls M04 Firebase Authentication, Mumbai Firestore and Google Drive. Attachment bytes travel directly from the generator/browser to Drive. Preview and Production share M04 Firebase/Drive quotas and marked test data, but no M01–M03 resources.

Complete response durations include this local connection, whereas sanitized server spans help identify application/provider work. Generator process CPU, event-loop lag, memory and request/transfer peaks are recorded; they do not measure every process or every condition on the machine/network. A second connection or an independent cloud generator is still needed to verify an apparent local-network bottleneck. API session load alone does not certify many-device rendering, event Wi-Fi or distributed arrival behavior.

# PPCP Google integration prototype

This is step 2: a Node backend and a small browser test page for a **personal test Sheet and Drive folder**. It does not use Apps Script. The same handler runs locally and as a Vercel Node function. There are no third-party runtime dependencies. The full React frontend and student authentication are later milestones.

## Start here

1. Install/use Node 22 LTS. Node 20.12+ also runs the local prototype; Vercel uses 22.x.
2. `.env.local` has already been generated with a random `TEST_ACCESS_KEY` and your test resource IDs. If absent, run `npm run setup` (it never overwrites an existing file).
3. Open `.env.local` in your editor. Fill **only** `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` from your Web application OAuth client. Leave `GOOGLE_REFRESH_TOKEN` blank locally. Never paste these values or tokens in chat, Git, or screenshots.
4. In the Google OAuth Web client, add the exact authorized redirect URI:

   ```text
   http://localhost:3001/oauth/callback
   ```

5. Confirm Sheets API and Drive API are enabled, your personal account is an OAuth test user, and both required scopes are configured in the consent screen:
   - `https://www.googleapis.com/auth/spreadsheets`
   - `https://www.googleapis.com/auth/drive`
6. Prepare the test Sheet as described below, owned by or shared with the personal Google account you will authorize. The file must be a **native Google Sheet**, not an `.xlsx` file merely uploaded to Drive.
7. Run:

   ```powershell
   npm run google:authorize
   ```

   Open the URL printed in the terminal, choose your personal test account, and grant both permissions. This consent URL contains no client secret or refresh token. The callback saves the refresh token to ignored `.local/google-oauth.json` and exits. The helper stops after five minutes if consent is unfinished. Do not run it through Vercel.
8. Run:

   ```powershell
   npm start
   ```

9. Open [http://localhost:3000](http://localhost:3000), enter `TEST_ACCESS_KEY` from `.env.local`, and click **Check Google connection**. Use localhost consistently; 127.0.0.1 is a different browser origin.
10. Submit synthetic information with two small attachments. Confirm the new Responses row and both files in Media, read the record back, and add a test remark.

PowerShell alternative if npm.ps1 is blocked: use `npm.cmd` instead of `npm`, or `node scripts/authorize.mjs` / `node server.mjs` directly. No `npm install` is needed.

## Upload design and limits

1. The protected API validates a file manifest, allocates Google file IDs and initiates resumable Drive uploads into the configured Media folder.
2. A signed two-hour ticket binds the IDs, expected names, types, sizes and submission ID. The browser receives per-file upload session URLs, never general Google access/refresh tokens.
3. File bytes travel from the browser directly to Google, avoiding Vercel's 4.5 MB function payload limit. The browser checks the acknowledged upload offset before retrying after a lost response.
4. Before appending a Sheet row, the API checks each completed file's folder, marker, name, declared MIME type and size through Drive. It also checks that the selected domain is active.
5. The record can be fetched and a remark appended using the same submission ID.

Limits use **decimal MB**: 5,000,000 bytes per file; 20,000,000 bytes total; maximum 10 files. Allowed: JPG/JPEG, PNG, WebP, PDF, DOC/DOCX, PPT/PPTX. Empty files, video, archives, executables and macro-enabled extensions are rejected. Extension and declared MIME checks are not content scanning or malware protection.

## API

All responses disable caching. Except health and unlocking, every endpoint requires the signed HttpOnly test-session cookie. All POSTs require `Origin` equal to `APP_ORIGIN` and `Content-Type: application/json`. Session duration: eight hours. This access-key gate intentionally replaces multi-user login only for the isolated prototype.

| Method/path | Purpose |
| --- | --- |
| `GET /api/health` | Node liveness only; does not claim Google connectivity |
| `POST /api/session` | `{accessKey}` → signed test-session cookie |
| `POST /api/logout` | Clear current browser cookie |
| `GET /api/checks` | Validate Google authorization, Responses/Remarks headers and writable Media folder |
| `GET /api/domains` | Read active domains from Calculations column C |
| `POST /api/upload-sessions` | `{files:[{name,size}]}` → submission ID, signed ticket, upload URLs |
| `POST /api/submissions` | `{ticket,email,name,studentId,program,domain,title,description,solution}` → verified/saved record |
| `GET /api/submissions?limit=20&offset=0` | Recent records; max page size 50 |
| `GET /api/submissions/:id` | Full record including media metadata |
| `GET /api/submissions/:id/remarks` | Feedback |
| `POST /api/submissions/:id/remarks` | `{remark}` → feedback with server-set author |

`email` is a synthetic test field here, not a production identity. No student can sign up through this prototype. No deletion, approval, status editing, or email sending endpoints are included.

## Verification

```powershell
npm test
npm run check:local
```

With the server running and Google authorized, `npm run google:smoke` checks the live connection without writing. `npm run google:smoke -- --write` creates **one synthetic submission, two tiny PNGs, and one test remark**, checks readback and sequential save retry, and retains the artifacts for inspection. It never logs credentials or upload session URLs. This exercises the live API from Node; browser CORS must still be checked using the test page.

Automated tests use fake Google responses and loopback HTTP. They cover authorization/CSRF, ticket tampering, file/total limits, 18-column data mapping, formula-safe writes, Google refresh coalescing, Google upload metadata, file verification, retry behavior, detail and remarks. They **do not prove a live OAuth consent, Google CORS, deployed Vercel routing, or a 60-user burst**. Those need real configured integration tests.

Manual acceptance:

- Connection check names the expected test spreadsheet and Media folder.
- One pain point with two attachments creates one correct Sheet row and two files in the test folder.
- Readback shows the complete description and attachment links; a test remark appears in Remarks.
- A file exactly 5 MB succeeds; files above 5 MB, more than 10 files or above 20 MB combined are rejected.
- Stop the network during upload and restore it: resumed uploads do not save incomplete files to a record.
- If the save response is lost, use **Retry saving uploaded files** without starting a new submission. Check the same fixed ID before retrying.
- Requests without the test cookie, forged tickets, and cross-origin writes fail.

## Vercel (next integration stage)

1. Deploy the project root containing `package.json`, `vercel.json`, `api/`, `src/`, and `public/`, using framework preset **Other**, Node 22.x. **Do not set the Root Directory to `public`**: that folder contains browser code, not the Node entry point. `vercel.json` explicitly disables framework autodetection, sets static output to `public`, runs `npm run check:deploy`, and routes only `/api/*` to the Node handler. Leave the dashboard Build Command override disabled, or set it to `npm run check:deploy`. Local OAuth/setup helpers are intentionally excluded by `.vercelignore`; both `npm run check` and `npm run check:deploy` check deployed files only. `npm run check:local` is the full local check. Avoid deploying from a parent directory containing credentials.
2. Set server-only environment variables: `TEST_ACCESS_KEY` (a different random value for deployment), `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REFRESH_TOKEN`, `GOOGLE_SPREADSHEET_ID`, `GOOGLE_MEDIA_FOLDER_ID`, and `APP_ORIGIN` (the exact stable HTTPS deployment origin, no trailing slash).
3. Copy only the refresh token value from local `.local/google-oauth.json` into Vercel's secret environment field yourself. Never put this JSON or `.env.local` into the deployment, client bundle, Git or chat. Local consent already issued the token; Vercel does not need a callback URL for this prototype.
4. Redeploy after setting the stable origin and credentials. Changing deployment hostnames requires updating APP_ORIGIN and redeploying. Preview origins are not automatically trusted. Keep deployment protection enabled where available.
5. Repeat the local acceptance tests. `/api/health` tests Node; `/api/checks` tests Google access.

### GitHub deployment troubleshooting

Local edits are not automatically copied to a connected GitHub repository. Commit/push the updated source to the branch Vercel deploys, then deploy that new commit. Redeploying an older deployment uses its old source. Confirm that Vercel's Source view has the current `package.json` (`check` delegates to `check:deploy`) and `vercel.json` (`framework: null`, `outputDirectory: public`). The Root Directory must be the directory containing both configuration files, not `public`. If browser code throws `document is not defined` inside a function, inspect root/framework settings and deployed source; browser `public/app.js` must be served as a static asset, and the function must be `api/index.js`.

## Deliberate prototype limitations

- Uses broad Drive access because the test folder predates the app and there is no Picker selection flow. Authorize a personal test account with no sensitive files. Production should review narrower scope/resource access or an approved organizational identity.
- External OAuth apps in Testing commonly issue seven-day refresh tokens with these scopes. If authorization expires, run `google:authorize` again and replace the deployed token. A stable production authorization strategy is a separate approval item.
- Google reads have bounded retries; mutations are not blindly retried. Repeated **sequential** saves with the same ticket return the existing ID. Simultaneous saves are **not exactly-once**: Sheets has no uniqueness constraint and this prototype does not implement distributed write coordination. Do not load-test writes against production.
- Pagination reduces response size but still reads Responses to find/filter records. There is no distributed cache or production quota protection yet; do not interpret this as a scale benchmark.
- Completed files remain in the test folder if submission saving fails or the tab closes. Nothing is automatically deleted after ambiguous network failures. The browser's ticket/retry state is memory-only and is lost on reload; inspect files/rows and clean up test artifacts manually. Drive files carry `prototype` and `submissionId` app properties for future reconciliation. There is no scheduled cleanup worker.
- Remarks are append-only and may duplicate on manual retries after an ambiguous response. Logout clears this browser cookie; individual session revocation and production rate limiting are not implemented. Keep the prototype restricted to one trusted operator.
- Attachment viewing uses Drive's own permissions. Private delivery to portal users without Google accounts, actual email verification, production password storage and existing-account migration remain out of scope for this integration test.
